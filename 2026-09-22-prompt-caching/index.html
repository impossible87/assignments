前缀缓存：为什么改一个字，整段就白算了

同一段长提示词，只在开头改了一个字符，第二次请求的账单却回到了原价 —— 变的不是模型单价，而是缓存整段失效了。这一页讲清缓存的边界在哪、什么会让它断，以及为什么 OpenAI 与 Anthropic 的用法完全不同。

    01

    它省的是一次重复计算，不是一次请求

    缓存的收益和"前缀有多长、被复用多少次"同时成正比。所以先记住三个数字。

    把一段提示词喂给模型时，最贵的一步是 Transformer 逐层算出每个 token 的 K/V 张量 —— 官方文档里叫 "prefilling"。如果这次的提示词开头和上一次完全一样，这段结果可以直接复用，只算新增的那一小段。[2]

    门槛

    1024 token

    OpenAI 的缓存对 1024 token 以上的前缀自动生效，低于这个长度一定不命中，cached_tokens 恒为 0；命中按 128 token 的倍数递增。[1]

    价格

    读 0.1×，写 1.25×

    Anthropic 的计费口径：5 分钟档写入 1.25 倍、1 小时档 2 倍，读取只要 0.1 倍。官方给的结论很直接：5 分钟档读 1 次就回本，1 小时档读 2 次。[5]

    延迟

    长提示词才明显

    官方实测：1024 token 时只快约 7%，150k token 时快 67%，最高可省约 80% 的首字延迟。提示词越长，缓存越值。[2]

    数据来源：OpenAI 官方 cookbook Prompt Caching 201 的两个实测点（1024 token 约 7%、150k token 约 67%）。[2]

    02

    缓存的是"前缀"，不是"内容"

    这句话决定了后面所有工程规则：只要开头不一样，后面再像也不算命中。

    两家的实现细节不同，但都遵守同一条物理约束：缓存键必须是"从头开始的一整段"。OpenAI 官方把它写成 exact repeated prefix match；Anthropic 则是"断点处的前缀哈希"，而且哈希是累积的 —— 断点之前的任何一块变了，哈希就变。[2][4]

    一个容易被忽略的细节：Anthropic 在读取时并不是"找稳定内容"，而是逐块向前回看，找之前请求已经写入过的条目。所以"把断点打在哪里"比"哪里内容稳定"更关键 —— 打得不对，回看也找不到东西。[4]

    页面上的数字是怎么算出来的

    量计算规则依据
    命中 token取"当前提示词"与"缓存里的上一次提示词"的最长公共前缀（逐字符比较）→ 按上面的口径换成 token → 向下取整到 128 的倍数；总长不足 1024 时命中一律记 0[1][2]
    两次请求的费用基础输入价记作 P。OpenAI 侧按官方表格里 gpt-4.1 的 75% 折扣（缓存读 0.25×P）；Anthropic 侧按 写 1.25×P、读 0.1×P[2][5]
    首字延迟降幅在官方两个实测点之间按长度做对数插值（1024 → 7%，150k → 67%），再乘以命中率；这只是量级演示，不是实测[2]

    05

    同一个机制，两家 API 长得完全不同

    OpenAI 是"自动 + 路由"，Anthropic 是"显式断点 + 回看"。这决定了你写代码时的手感。

    维度OpenAIAnthropic
    怎么开启自动：超过 1024 token 的请求自动缓存，不改代码显式：请求体顶层加 cache_control，或在具体内容块上打断点
    缓存键前缀完全相同 + 落在同一台机器断点处的前缀哈希（累积）
    位置标记无块级标记；用 prompt_cache_key 提高路由命中块级 {"type":"ephemeral"}，可带 "ttl":"1h"
    有效期内存缓存默认生效；可选 24 小时延长默认 5 分钟，命中免费刷新；可选 1 小时
    最小长度1024 token（低于则不命中，不报错）按模型 512 / 1024 / 2048 / 4096 token
    观测字段usage.prompt_tokens_details.cached_tokenscache_creation_input_tokens / cache_read_input_tokens

    OpenAI 侧字段语义取自官方 OpenAPI 规范里的 prompt_cache_key、prompt_cache_retention、prompt_cache_options。[3] Anthropic 侧取自官方 Prompt caching 文档。[4]

    价格倍数：同样是命中，省下的幅度差很多

    缓存读取相对基础输入价的倍数（越小越省）

    缓存读取缓存写入（仅 Anthropic 显式计费）

    OpenAI 各档折扣来自官方 cookbook 的模型对照表（本页取 gpt-4.1 / gpt-5.2 / gpt-4o / gpt-realtime 四档示例）；Anthropic 的 1.25×／2×／0.1× 来自官方定价页。[2][5]

    06

    反刍：Hermes 自己是怎么保证"前缀稳定"的

    教科书说"静态放前面、动态放后面"。真实的 agent 得在代码层面把这件事钉死。

    我把 Hermes 的相关源码取了下来（prompt_cache_boundary.py、prompt_cache_scope.py、prompt_caching.py 与官方 prompt-assembly 文档），对着上一节那份失效清单读，能看出四个刻意的设计。[6]

    01 边界

    登记，而不是猜

    拼接方在组完消息后调用 register_stable_prefix() 把稳定前缀登记下来，请求时只认已登记的那一段。源码注释写明了为什么不用分隔符解析："markers can legitimately appear inside skill bodies" —— 标记可能合法地出现在技能正文里，任何启发式都会缩小缓存前缀，或者把易变内容吸进去。[6]

    02 断点

    固定 4 个，共享一个 TTL

    默认布局是四个 cache_control 断点：稳定系统前缀、稳定边界处、以及最近 3 条消息。Anthropic 的硬上限正好是 4 个断点，所以这个数字不是随便取的。[6]

    03 TTL

    按"谁在驱动会话"选档

    AUTO_CACHE_TTL = "auto"：定时任务、子代理、webhook、批处理这类机器驱动的会话，节奏和人工对话完全不同，5 分钟档会频繁过期，所以按来源自动选档。[6]

    04 作用域

    跨压缩轮换仍然稳定

    会话被压缩时会换物理 session_id，如果直接拿它当缓存键，压缩一次缓存就进新桶。prompt_cache_scope.py 把它映射到压缩谱系的根，托管方按响应粒度发 id 时另用 gateway_session_key 哈希成 gwk_<sha256[:24]>。[6]

    官方组装文档里还有一句值得记：已缓存的系统提示词按固定顺序拼装，时间戳和会话 ID 放在最后一层，文档原话是"这种分离使稳定前缀保持稳定，从而有效缓存"；而临时覆盖层（HERMES_EPHEMERAL_SYSTEM_PROMPT、prefill 消息）被刻意排除在缓存前缀之外。[6]

    对照下来，上一节那份失效清单里的每一条，Hermes 都有一处对应实现：时间戳别进前缀 → 组装顺序把它放最后一层；工具顺序会失效 → 断点位置由构造方显式登记；5 分钟太短 → TTL 按驱动方自动选；换 id 就换桶 → 作用域映射到谱系根。

# Prompt 日志：LMAPI 知识网页（子任务 C · Prompt Caching / Prefix）

子任务：**C. Prompt Caching / Prefix —— 为什么前缀稳定能省钱**

主要参考官方文档：

- OpenAI 官方 OpenAPI 规范（字段语义）：https://github.com/openai/openai-openapi/blob/main/openapi.yaml
- Anthropic *Prompt caching*：https://platform.claude.com/docs/en/build-with-claude/prompt-caching

> 说明：下面的每一轮都对应仓库里真实发生过的改动（Agent 协作产出 + 本人校对）。
> 规则是任务书要求的「规格 → 失败 → 迭代」，每轮只记"改了规格的哪一部分"和"现象怎么变的"。

---

## 轮次 −1（规格阶段）：先写 AGENTS.md，再让 Agent 动手

**第 0 版规格**只写了「做一个可交互的 prompt caching 讲解页」。

**失败现象**：Agent 交回来的第一版是个"概念罗列页" —— 名词解释齐全，但没有任何一个能动手的东西，
更没有"改一个字会怎样"的演示。这正是任务书提醒的"一键生成后交差"。

**改动了规格的哪部分**：在 `AGENTS.md` 的 Constraints 里把"必须有一个 demo"写成了可验收的形式：

> 必须有一个能动手的 demo：改动前缀里的一个字符 → 命中区间断裂 →
> **命中率、首字延迟、费用三个数字同时重算**。数值计算规则要印在页面上，不能是黑箱。

**效果变化**：第二版才开始出现"四个块 + 实时重算"的结构。这条改动也让我后面每一次
"Agent 跑偏"都能用同一句话纠回来（把要求写成可验收的句子，而不是形容词）。

---

## 第 1 版 Prompt：要给"命中"下定义

**规格片段**：`命中 = 与上一次请求的最长公共前缀`。

**失败现象（内容错误）**：Agent 按这个定义做出的演示，命中率永远是 100%，
连"把系统提示词开头改一个字"都显示"仍然命中"。原因是规格里漏了官方两条硬约束：
命中按 **128 token 粒度**递增、总长低于 **1024 token** 一律不命中。

**第 2 版规格（补哪部分）**：

> 命中 token = 最长公共前缀换算成 token 后**向下取整到 128 的倍数**；
> 提示词总长不足 **1024 token** 时命中记 0。（OpenAI 官方：命中以 128 token 为粒度递增）

**效果变化**：演示终于能区分"末尾改（仍然命中）"和"开头改（整段失效）"。
这一轮也让我确认：**规格里凡是数字，都必须带着官方出处一起写**，否则 Agent 会用"看起来合理"的规则填坑。

---

## 第 2 版 Prompt：token 换算口径

**规格片段**：只写了"按字符数估算 token"。

**失败现象（数字不合理）**：演示里那段提示词总长显示 **601 token**，
**低于 1024 门槛**，于是整个演示永远不可能命中 —— 演示本身失效了。
根因是"字符数 ÷ 3.6"这个口径对中文是错的（中文一字往往多于一个 token）。

**第 3 版规格（补哪部分）**：

> token 估算：中文按 1 字 ≈ 0.67 token、英文按 4 字符 ≈ 1 token；
> 并在页面上标明这是估算口径，不是真实 tokenizer。

**效果变化**：同一段提示词变成 ≈1,540 token，稳稳落在门槛之上，
演示第一次出现了那条阶梯：末尾改 → 仍 100%；文档中间改 → 掉到 50%；开头改 → 归零。

---

## 第 3 版 Prompt：让"中间地带"可见

**失败现象（演示不完整）**：只有"末尾改"和"开头改"两个动作，读者会以为世界只有两种结果。

**第 4 版规格（补哪部分）**：增加一个动作——**改参考文档中间的一条**；
并要求三个动作的费用一起对比（改得越靠前，失效越多）。

**效果变化**：三档成本差被显式拉开（同一次请求，`$0.0058 → $0.0075 → $0.0092`），
"前缀稳定"这件事第一次有了价格标签。

---

## 第 4 版 Prompt：把"来源不可达"写进规格

**失败现象**：Agent 报告"OpenAI 官方文档页拿不到"，一度准备改用二手博客的数字。

**第 5 版规格（补哪部分）**：

> 只用一手来源。若某厂商文档页在当前网络不可达，必须改走该厂商的**官方仓库 / 官方规范**
> （cookbook、OpenAPI、llms-full.txt），不许退化成博客；并在页面上写明取材通道。

**效果变化**：OpenAI 侧改用官方 cookbook（拿到 1024/128 门槛、折扣表、TTFT 实测两点）
与官方 OpenAPI（拿到 `prompt_cache_key` / `prompt_cache_retention` 的字段语义）；
Anthropic 侧用官方 `llms-full.txt` 整包文档（拿到 1.25×／2×／0.1× 与"读 1 次回本"）。
页面结尾因此多了一段"取材通道说明"——它本身也成了内容深度的一部分。

---

## 第 5 版 Prompt：实现层的两个坑（记录在案）

1. **类名撞车**：演示块用了 `.seg` 作为类名，正好撞上模板里主题切换控件的 `.seg`
   （那是 `display:inline-flex`），结果每个块的头部被挤成竖排。
   → 规格里补上：**新组件的类名一律加前缀**（最终改成 `.pseg`）。
2. **HTML 里写了 Markdown**：正文用了 `**加粗**`，浏览器不解析，页面上直接显示星号。
   → 规格里补上：**正文只允许用 HTML 标签表达强调**，交付前全量搜索 `**`。

## 结论

**这个知识点最该用哪一层解决？**

□ Prompt　□ Schema　■ **Runtime**　□ Eval

理由：缓存能不能命中，不取决于提示词写得多漂亮，而取决于**请求的结构与运行时参数** ——
稳定的前缀顺序、断点打在哪里、TTL 选 5 分钟还是 1 小时、同类流量用同一个
`prompt_cache_key` 做路由粘性、并发时序怎么安排。Hermes 的源码也印证了这一点：
它把"稳定前缀"做成**构造方显式登记的边界**（`prompt_cache_boundary.py`）、
固定 4 个断点、按"谁在驱动会话"自动选 TTL、并把会话作用域映射到压缩谱系的根 ——
全部是运行时机制，而不是提示词技巧。

**一句话总结这次学到的 Prompt Engineering 方法**：

> 与其反复描述"我要什么效果"，不如把**可验收的判据**写进规格 ——
> 数字要带出处、规则要能自证、失败现象要能被下一次迭代直接对上。
> 规格写得越像测试用例，Agent 的产出就越少需要返工。
